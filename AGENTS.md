# Efficient validation on the current desktop

- Use `Source/Scripts/Build.ps1` for builds and `Source/Scripts/Test.ps1` for tests. These launch background-priority process trees on the current desktop; do not bypass them with naked smoke-test commands or parallel validation jobs.
- Tests are mandatory after every application change, including small UI/layout changes. Run the relevant groups against the current source/configuration and require them to pass before publishing or reporting the change complete. A successful build or publish does not replace tests; do not wait for the user to request testing.
- Run only groups relevant to the change. `-Group address` is sufficient for path-model changes; use the matching `-UIGroup` for GUI behavior. Do not rerun all groups for every small layout edit, diagnostic retry, or publication.
- UI checks run only when explicitly selected, on the current Windows desktop with software rendering and an owned filesystem root. The user explicitly requested removal of separate-desktop testing. Test windows, menus and dialogs may appear; do not create or switch desktops, move the user's pointer, send global keystrokes or explicitly activate test windows.
- Prefer the smallest relevant group. Use `-UIGroup operations` for create/rename/dialog behavior instead of the full UI suite. Combine related groups in one invocation so each project builds once. Use `-SkipBuild` only when the selected binaries are already built from the current source/configuration; rebuild after source changes.
- `Source/Scripts/Build.ps1` defaults to build only. Publish/package only when needed. Do not close or restart the user's running application solely for validation; the publication workflow below is explicitly authorized.
- The user expects completed application changes to be published to `Publish/CDirWinX64`. After the required tests pass, run `Source/Scripts/Build.ps1 -Publish`; packaging is needed every new publishment.
- After every successful publication, regenerate `Artifacts/CDirPreview.png` from the current release and update its companion metadata with the exact release version and capture time. Also update `Docs/Images/CDirPreview.png` on every publication with an identical copy of the current release preview, verify that both image files have the same SHA-256 hash, and synchronize the preview version labels in both language sections of `README.md`. Keep the documentation image included in Git so GitHub can display it while `Artifacts/` remains ignored. Inspect the image before reporting completion; never retain a preview from an older release as the current preview. Archive superseded previews and obsolete diagnostic artifacts into a unique workspace `Trash` subdirectory, preserving their relative paths and the current release ZIP and validation evidence.
- Outputs and reports under `Artifacts` are intermediate validation results, not a completed delivery. After the relevant tests pass, always publish the latest tested application to `Publish/CDirWinX64` and its latest versioned ZIP to `Publish`. Before reporting completion, verify that the executable, `Release.json`, and ZIP in `Publish` match the tested release version and that the `Publish` ZIP is identical to its `Artifacts` copy; never leave the newest successful release only in `Artifacts`.
- Release archives must use ZIP format and be saved under `Artifacts` with the exact filename `CDir_WinX64_v<major>.<minor>.<patch>.zip`, for example `CDir_WinX64_v0.0.0.zip`. Derive the filename's version from the published `Release.json`; it must match the executable metadata, title-bar version, and packaged `Release.json`.
- Each release ZIP must contain exactly one top-level folder named `CDir_WinX64_v<major>.<minor>.<patch>` (the ZIP filename without `.zip`), so extracting it creates that versioned folder. After packaging, save an identical ZIP in `Publish` as well as `Artifacts`, verify both copies match the current published version and contents, and move obsolete fixed-name `CDirWinX64.7z` or `CDirWinX64.zip` packages into a unique workspace `Trash` subdirectory. Keep the runnable application updated at `Publish/CDirWinX64`; successful publication must update the timestamps of that directory and its `Publish` parent.
- After every successful publication and ZIP packaging, add a release entry to `UpdateLog.md` in the current workspace root. Include the exact published version, the publication time to the second with timezone (`YYYY-MM-DD HH:mm:ss UTC+08:00`, Asia/Shanghai), and the specific changes in that release. Preserve existing entries; do not record failed builds or publications as completed releases.
- Keep release entries in `UpdateLog.md` sorted by publication time in descending order: the newest release goes first, directly below the document heading, and the oldest release goes last. Insert new releases at the top of the release history rather than appending them at the end; preserve all existing release content when reordering.
- Release versions use `major.minor.patch` and appear in the title bar as `vmajor.minor.patch`, starting from `v0.0.0`. Use the version workflow in `Source/Scripts/Build.ps1` and the persisted state in `Source/Version.props`; keep the title-bar version, executable metadata, and packaged `Release.json` consistent.
- The major version is completely user-controlled. Change it only on explicit user instruction, using `-MajorVersion` or editing the first component in `Source/Version.props`; never advance it automatically.
- When the user manually changes the major version, automatically reset both minor and patch to 0 so that release is exactly `major.0.0` (for example, `0.2.36` becomes `1.0.0`). This reset takes precedence over automatic minor and patch increments for that release; subsequent releases resume the normal increment rules.
- For a release fixing an actual severe fatal bug, such as a crash, unresponsive hang, or interference with other applications, use `-FatalBugFix` to increment the minor version once after success. Temporary unavailability of the browsing window during a file operation alone does not qualify as a fatal bug. For a major new feature, increment the minor version only when explicitly requested by the user, using `-FeatureRelease`. Ordinary fixes, features and layout changes leave minor unchanged. Combining `-FatalBugFix` and `-FeatureRelease` increments minor only once; neither resets patch or changes major.
- When source or configuration in `Source` changes, the next successful release automatically increments patch exactly once, only after build, publication and ZIP packaging all succeed. Never manually increment patch. Build-only runs, tests, failed releases, and republishing or repackaging unchanged source must not advance patch; repeating fatal-fix or feature flags for already published unchanged source must not advance minor either.
- When testing a release candidate, use `Test.ps1 -PublishConfiguration` with the same `-FatalBugFix` or `-FeatureRelease` options that will be used for publication. Reading a candidate or retrying a failed release must not consume version numbers.
- Before publishing, check for running instances whose executable path exactly matches this workspace's resolved `Publish/CDirWinX64/CDir.exe` path (case-insensitive). The user explicitly authorizes force-killing those instances without further confirmation. Verify each process's executable path before terminating it, and wait for those processes to exit before publishing. Never terminate other applications or CDir instances from other paths; if a process path cannot be verified, do not kill it.
- Before any publication stop, preserve each verified user instance's live workspace through `Source/Scripts/PublicationWorkspace.ps1`, together with the existing settings and backups. If capture or verification fails, stop without killing the instance. After the instances exit, restore the most recently active complete snapshot before restarting. `Build.ps1 -Publish` performs this preservation and restart itself; do not bypass it by force-killing first. Keep the per-instance recovery snapshots under `Build/PublicationWorkspaces`.
- UI checks, including `-Published`, must never register as user instances, discover or clone user windows, pause user autosaving, or read/write settings outside their owned test scope. Verify this isolation when changing persistence or test startup behavior.
- If a published instance was running before publication, reopen the published `CDir.exe` once after publication succeeds. If no published instance was running, do not launch one automatically. If publication fails, report the failure and do not launch a partially updated application.
- Do not run multiple validation processes at once. The runner also serializes jobs across script invocations. Do not change priorities or terminate unrelated IDE, user application, or system processes.
- Before every new test invocation, move all files and folders produced by the preceding test invocation into this workspace's `Trash` directory, then verify the move has completed before starting tests. This includes its complete `Artifacts/TestRuns/<run-id>` directory (reports, screenshots, progress/error logs, and other outputs) and any retained owned temporary test directory. Verify paths and ownership before moving, preserve the original directory structure in a unique Trash subdirectory, and never overwrite earlier archived files or move an active test's files, test source code, or published application files. Related groups in one `Test.ps1` invocation are one test run and remain serialized as required above.
- The user explicitly prefers fast tests over CPU caps: CPU rate and affinity are unrestricted by default. Do not reintroduce a single-core or CPU-percentage limit unless requested. Keep very-low I/O priority and owned test directories; if process-tree or I/O protections cannot be established, stop rather than bypass the runner.
- Keep normal memory page priority for test/build children. The runner already enforces Idle CPU and very-low I/O scheduling; do not repeat `PROCESS_MODE_BACKGROUND_BEGIN` in launched tests, which aggressively trims WPF's working set and slows startup.
- Report which groups ran and which did not. Previous full-suite pass counts are historical evidence, not validation of a new change.
- All menus must always use a compact layout with readable fonts. Preserve appropriate or user-configured font sizes; minimize menu and item padding, margins, and unused icon, shortcut, or submenu gutters instead of shrinking the text.
- Use sentence case for app-authored English explanations, tooltips, confirmation messages, errors, progress messages, and status or empty-state hints: capitalize the start of each sentence, not every word. Use Title Case for functional UI captions such as menus, buttons, window and section titles, field labels, and options, including short words such as In, To, And, and The. Preserve acronyms, keyboard key names, brand names, and user-provided filenames, paths, and category names.
